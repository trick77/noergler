## Almanach note

You just reviewed this pull request. Now write a scratch note for Almanach, a knowledge base kept outside this review, about what the PR teaches about repository `{repo}` in Bitbucket project `{project}`. Facts about the system, never about the PR's quality, the review or your findings.

## Fields

- `summary`: one paragraph on what the PR does to the system, at most 600 characters. `null` when the PR teaches nothing about the system (a dependency bump, formatting, a rename); then every list below is empty.
- `change_kind`: `bugfix`, `feature`, `refactor` or `chore`. The ticket type below is a hint; the diff decides.
- `bugfix`: only for a bugfix, else `null`. `symptom`: what went wrong for the user or the system, one sentence. `cause`: why, as the code shows it, one sentence. `cause_kind`: `logic`, `concurrency`, `config`, `input_validation`, `integration`, `missing_test` or `other`.
- `components`: modules, services, packages or screens the PR touches, and what each is for.
- `rules`: business rules the code enforces.
- `invariants`: what must always hold, as the code shows it.
- `entities`: data entities, tables, messages, with their key fields.
- Each item: `name` (at most 80 characters), `text` (one sentence, at most 300 characters), `files` (up to 5 repository paths from the files you saw, exactly as shown). At most 8 items per list. Nothing a reader learns from a file name alone.

## Never

Code, line numbers, commit hashes, UUIDs, credentials or config literals, PR numbers, dates, names of people, your findings, and statements about other repositories or the project as a whole: you saw this repository only.

## Limits

The whole note is discarded unread when any field exceeds its limit or the note exceeds {note_max_chars} characters in total. Prefer fewer items to a discarded note.

{output_language}

The note is German whatever language the review above was written in: every `summary`, `name`, `text`, `symptom` and `cause`. `files`, enum values and JSON keys stay as they are.

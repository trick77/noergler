The PR author asked you to resolve the merge conflict of their pull request. The target branch `{target_branch}` is being merged into the PR's branch `{source_branch}`. Below is each region both branches changed differently since their merge base. Choose, for each, the lines the merged file keeps there. Nobody builds or tests the result before the author reviews it, so choose only what is plainly right.

## What you see

Each conflict shows, for one spot in one file:

- `B` lines: the merge base, before either branch changed it. For understanding only: never choose them.
- `T` lines: what the target branch `{target_branch}` has there now.
- `S` lines: what the PR's branch `{source_branch}` has there now.
- A few unchanged lines before and after, for context.

## Rules

- Answer each conflict with the list of line ids the merged file keeps there, in order: `T3`, `S1`. Never text, never a `B` id.
- Keep each branch's lines in their own order: `T2` never before `T1`, `S2` never before `S1`. You may interleave the two branches.
- Read each branch against `B` first. A `B` line that one branch kept as it was and the other branch changed or deleted is the other branch's change: the merged file follows the change. Never keep such a line: keeping it undoes that branch's work, a deletion included.
- Keep both branches' changes where both belong: a line each branch added, a list entry, an import.
- A line both branches have with the same meaning, keep once.
- Where the two branches changed the same line in ways that cannot both stand, keep one version only when it already carries what the other one changed (the same fix, plus more); the other is dropped, and every dropped line is shown to the author. When neither version carries the other's change, it is not yours to pick: infeasible.
- Set `feasible` to false, with `resolutions` empty, when a conflict needs a line neither branch has (combining two edits of one line into a new one), a decision only the author can make, or more than choosing lines. That includes: one branch deleted lines the other branch changed; following both branches' changes leaves no line to keep; and generated or built files (hashes, bundles), which only a rebuild resolves. Then `reason` says why, in one sentence, for the author. One such conflict makes the whole answer infeasible: all or nothing.
- `reason` is empty when `feasible` is true.
- One entry in `resolutions` per conflict, its `conflict` number as shown.

## Output format

Respond with a single JSON object and nothing else:

```
{"feasible": true | false, "reason": "<one sentence or empty>", "resolutions": [{"conflict": 1, "lines": ["T1", "S1"]}]}
```
